# Runtime startup self-check and Order recovery

Status: source implementation and isolated verification completed on 2026-10-24;
participant restart/unlock and legacy settled-Order reconciliation were reported.
Full login/reboot and missing-result restoration are not established. See verification and limits (private historical evidence; not distributed).
The source review table below records the pre-change findings.
This plan precedes discussion of `./run update`; it does not authorize real funds,
new Orders, deletion of participant history, or widening Wallet authority.

## Required behavior

Start Runtime's safely configured local listener before asynchronous Order checks.
A historical business record, locked Wallet, unavailable network or old routing
format must not cause a restart loop. Report separately: process liveness,
self-check progress, Wallet availability/lock/Policy state, and purchase readiness.
An authenticated status view explains blockers and the next action without exposing
private input/output, signatures or credentials. Public health remains minimal.

This is not permission to listen without caller authentication, bind publicly,
overwrite a live socket/port, or ignore unsafe installation ownership. If the
listener itself cannot safely start (occupied port, missing/unsafe authentication
material), the CLI must explain repair; do not claim that every configuration can
produce a running HTTP server. Wallet capability failure may disable Wallet actions
without disabling an otherwise safely authenticated status listener.

Run local checks first, then reconcile eligible historical Orders in a bounded
background queue. Self-check does not prepare an Order, sign/submit a payment,
request service authorization, execute a Provider request, confirm receipt, cancel
an Order, or revoke/change Policy. These remain existing explicit invocation or
administrative flows. The existing Settlement workers own automatic closure/refund.

## Two independent outcomes

A financial terminal state (Released, Refunded or Cancelled) is separate from
verified local result availability. Delivered is not financial finality. A cached
result does not establish payout; payout does not establish that the client saved
or received the output. Store observations with source, identity and observed-at
epoch time; retain original invocation/request/Order identities and replay fences.
These are local projections, not new Protocol enums or rewritten wire states.

## Recovery matrix

| Observed condition | Startup self-check / permitted recovery | Purchase boundary and user action |
| --- | --- | --- |
| No history in a genuinely new installation | Complete local inventory; inspect Wallet/configuration | Normal readiness still required. Missing history in a previously used installation is not proof of a new installation. |
| Wallet missing, stopped, locked or unbound | Keep Runtime available; expose specific dependency status; retry after dependency changes | No payment without Wallet's existing checks. Prompt start/unlock/setup as appropriate. Never save an unlock secret. |
| Settlement/network unavailable or maintenance | Keep last observation explicitly stale; retry boundedly with backoff | Do not claim finality or replay a payment. Unresolved affected calls wait. |
| Valid current history and verified cached result | Validate result binding; separately reconcile financial status | Same-call result reuse needs no new payment; report any pending financial check separately. |
| Invocation exists, no saved Order ID | Preserve orderRequestId and commitmentNonce; inspect what read APIs can establish | Lost prepare response may still mean an Order exists. Self-check must not call prepare as a substitute for read. Only original explicit resume may use its established idempotent path. |
| Signed payload saved, payment outcome unknown | Read original Order/funding evidence using saved identity | Neither paymentSubmitted false nor a timeout proves no funding. No replacement Order, nonce or signature generated by self-check. |
| Funded, not yet accepted | Observe acceptance/closure/deadlines | Do not cancel because Provider briefly goes offline. Existing user cancellation and Settlement timeout rules apply. |
| Accepted, still executing | Observe original Order and deadline | No new service execution in background. Resume original request explicitly; accepted service deadline remains authoritative. |
| Delivered, payout pending | Track finalization/refund/closure observations separately from output cache | No startup receipt acknowledgement or accelerated payout. |
| Released, verified result saved | Persist verified financial observation; retain result and request replay fence | Same request returns existing result where its format is supported; no purchase. |
| Released, result absent or incompatible | Record settled transaction and unavailable/unverified result separately | Do not rerun the service or fabricate output. Existing Provider result retrieval may be used only if supported by the original contract and authorization; otherwise explain limitation. |
| Refunded or Cancelled | Persist verified terminal observation, preserve request identities and any valid result evidence | Same request stays terminal, not a fresh purchase; refunds do not restore cumulative Policy spend. |
| Legacy routing record | Preserve original bytes, IDs and binding; reconcile independently of current call routing where authoritative identity is available | No automatic routingVersion addition or coercion into new service context. Known request stays fenced; terminal history need not block unrelated new calls once scope is safely known. |
| Corrupt/unknown schema, conflicting IDs, unsafe file or write failure | Preserve source; report repair needed; isolate only if records can be reliably identified | If affected scope is unknown, pause all new paid calls while status stays available. Never replace unreadable state with an empty store. |
| Order not found, chain/Factory/Policy/deployment changed | Keep unresolved; require matching original deployment and identity evidence | A 404 or wrong current deployment does not mean unpaid. Do not silently query new deployment as if it owned the old Order. |
| Local and authoritative observations conflict, or finality is insufficient | Preserve evidence and mark pending/review; recheck matching source | Do not pick a convenient terminal result or release replay protection. |

## Identity, authority and scope

Use Wallet's formal `readSettlementOrder` IPC and Settlement's Buyer-scoped read
endpoint; a normal User never reads server SQL or operator files. Today that HTTP
read requires a signed authentication request. Wallet locked means remote checks
wait for unlock; do not bypass authentication or add anonymous Order disclosure.
Signing a read authentication request is not payment signing.

Match Order ID, Buyer, chain, original Vault/Factory/Policy when available, service
reference and request hash. Persist only verified observations. For historical
records whose deployment facts cannot be recovered reliably, report the gap rather
than guessing. Optional independent chain verification must use the exact original
identity and existing finality policy; changing chain rules is outside this plan.

The participant's one legacy Order has independently observed Released state and
zero Vault balance on private Anvil. This proves the scoped chain observation,
not client result availability or a fresh Settlement database reconciliation.
Do not hard-code that Order or the reference random service into implementation.

Until initial inventory establishes a trustworthy replay boundary, block new paid
calls. After inventory, isolate known affected requests; allow unrelated requests
only when duplicate-payment scope is reliably bounded and normal Wallet/Settlement
readiness passes. Global pause remains valid for unreadable/conflicting history.
An explicit new user request (`--force`) is not an automatic recovery fallback.

## Concurrency, persistence and scheduling

- One self-check scheduler per Runtime; bounded batch/concurrency and timeouts,
  capped retry backoff with jitter. Wake on restart and dependency recovery;
  no unbounded timers, pending promises or frequent polls of confirmed terminal Orders.
- Serialize background observations with foreground invocation updates. A stale
  read must not overwrite a newer outcome; merge observation metadata without
  mutating immutable request/Order/payment identities.
- Persist recovery observations atomically and durably. Crash during checking,
  writing or restart resumes the same work. No archival or format migration that
  opens a window for a known invocation ID to become a new purchase.
- Do not remove replay fences/results on terminal detection or introduce indefinite
  new copies of private payloads. Any archive schema/retention change is reviewed
  separately; preserve existing source history in the first implementation.
- Stop scheduling on shutdown and bound outstanding calls. Status counts distinguish
  checked, waiting on dependency, unsettled and needs-review; no misleading all-clear
  based solely on an empty queue or a successful `/health` response.

## Implementation and acceptance order

1. **Safe startup and local inventory.** Separate liveness/readiness, retain replay
   fences, classify legacy/corrupt/current records and dependency failures. Test
   the actual process starts with a valid secure listener despite old history;
   affected/unknown-scope paid calls are fenced and state bytes remain unchanged.
2. **Read-only Order reconciliation.** Use formal authenticated reads, independent
   financial/result observations, durable writes, bounded retries and concurrency.
   Test all matrix branches including absent Order ID, wrong identity, locked Wallet,
   maintenance, incomplete funding, terminal state and conflicting cache. Any shared
   API/storage change requires consumer review before implementation.
3. **Recovery and upgrade handoff.** Present actionable status in `./run status`
   and install/setup; verify restart during scans/writes, race with active calls,
   repeated restarts and no duplicate payment. Preserve known request IDs through
   any approved legacy handling. Use maintained fixtures with at least two business
   payloads and official connectivity material only.
4. **Participant acceptance.** Re-read the supplied desktop record, reconcile with
   matching authority, and verify Runtime stays running, old request cannot trigger
   a new purchase, and Wallet lock/unlock does not restart Runtime. Additional paid
   acceptance needs explicit scope; do not rerun connectivity purchase automatically.

Each loop gets focused tests and evidence before the next. Mock tests do not prove
real process restart, chain settlement or participant usability. `./run update`
remains a subsequent design discussion, not part of this implementation approval.
